# تمرین ۶: سه راه برای خبر گرفتن

> جلسهٔ ۶ · مهلت: شب پیش از جلسهٔ ۷

## هدف

یک خوراک خبر را با سه سازوکار به کلاینت می‌رسانید و هزینهٔ هر کدام را اندازه می‌گیرید: تأخیر، بایت، و اینکه از پشت یک واسطهٔ ناسازگار زنده می‌ماند یا نه. در پایان باید بتوانید برای یک نیاز مشخص بگویید کدام را برمی‌دارید و چرا.

## پیش‌بینی (سر کلاس نوشتید؛ همان را در README بیاورید)

سرور شما پشت proxy تمرین ۵ است؛ همان که پاسخ را کامل می‌گیرد و بعد می‌فرستد. از میان polling و SSE و WebSocket، کدام کار می‌کند و کدام نه؟ برای هر کدام یک جمله دلیل بنویسید.

## کار پایه

فایل‌های `starter/` را بردارید (Node 22؛ هیچ بسته‌ای لازم نیست):

```sh
HEARTBEAT=1000 node server.mjs      # http://127.0.0.1:8811
```

مسیرهای `POST /publish` و `GET /poll?since=N` آماده‌اند. فایل `ws-lite.mjs` کمینهٔ WebSocket است: آن را بخوانید، ولی عوضش نکنید. دو کار در `server.mjs` با شماست:

1. **جریان SSE در `/events`.** هر خبر با `id` و `data`؛ خبر تازه بی‌درنگ برسد؛ با `Last-Event-ID` فقط خبرهای جاافتاده؛ هر `HEARTBEAT` میلی‌ثانیه یک خط توضیح؛ و header‌هایی که نگذارند واسطه پاسخ را نگه دارد یا جمع کند.
2. **اتصال WebSocket در `/ws`.** هر خبر یک پیام متنی JSON به شکل `{"id":N,"data":"…"}`؛ با `?since=N` اول خبرهای جاافتاده؛ و اگر `Origin` آمده و با `ALLOWED_ORIGIN` یکی نیست، پاسخ `403` بدون handshake.

با curl بیازمایید (در پنجرهٔ دوم خبر منتشر کنید):

```sh
curl -sN http://127.0.0.1:8811/events
curl -s -X POST -d 'first news' http://127.0.0.1:8811/publish
curl -sN -H 'Last-Event-ID: 1' http://127.0.0.1:8811/events
```

خودآزمایی:

```sh
node check/check.mjs
```

بعد اندازه بگیرید و جدول را پر کنید:

```sh
node measure.mjs                    # هر سه سازوکار، مستقیم
POLL=5000 node measure.mjs poll     # polling کندتر
```

| سازوکار | تأخیر میانه | بایت به ازای هر خبر | چرا این‌قدر؟ |
| --- | --- | --- | --- |
| polling هر ثانیه | | | |
| polling هر پنج ثانیه | | | |
| SSE | | | |
| WebSocket | | | |

کد را در `ex06/server.mjs` مخزن خودتان بگذارید، و خروجی خودآزمایی و اندازه‌گیری را در `evidence/`.

## چالش

- **واسطهٔ ناسازگار.** فایل `proxy.mjs` تمرین ۵ را جلوی سرور بگذارید (`ORIGIN_PORT=8811 node proxy.mjs`) و اندازه‌گیری را از پشت آن تکرار کنید: `PORT=8790 node measure.mjs`. نتیجه را با پیش‌بینی‌تان مقایسه کنید. برای هر سازوکاری که شکست، بگویید دقیقاً کدام رفتار proxy مسئول است.
- **کلاینت کُند.** کلاینتی را تصور کنید که وصل می‌شود ولی نمی‌خواند. با `ws.buffered()` ببینید چند بایت برای او در صف مانده، و یک سیاست پیاده کنید: از حدی که خودتان انتخاب می‌کنید به بعد، چه می‌کنید؟ آزمون: `node check/check.mjs --slow`. در README بنویسید چرا این سیاست را برداشتید و چه چیزی را فدا کردید.

## امتیازی

- مسیر `/longpoll?since=N` را بسازید و به `measure.mjs` بیفزایید. جایش در جدول کجاست؟ از پشت proxy کار می‌کند؟
- یک صفحهٔ HTML کوچک بسازید که با `EventSource` به `/events` وصل شود. سرور را ببندید و دوباره بالا بیاورید؛ در زبانهٔ Network مرورگر، درخواست دوباره و `Last-Event-ID` آن را پیدا کنید و تصویرش را بگذارید.

## تصمیم مهندسی

سامانهٔ نوبت‌دهی آزمایشگاه سه نیاز تازه دارد: خبر دادن آزاد شدن یک نوبت، نمایش زندهٔ صف پذیرش روی یک نمایشگر، و گفتگوی متنی بیمار با پذیرش. برای هر کدام یک سازوکار انتخاب کنید و در دو جمله بگویید چرا، و اگر اتصال قطع شد کلاینت چه می‌کند.

## پل به جلسهٔ ۷

کلاینت SSE شما بعد از هر قطعی خودش دوباره وصل می‌شود. اگر هزار کلاینت این‌چنینی داشته باشید و سرور یک لحظه بیفتد، در ثانیهٔ بعد چه می‌شود؟ یک جمله بنویسید که سرور چطور می‌تواند به کلاینت بگوید «الان نه؛ بعداً بیا». جلسهٔ ۷ از همین‌جا شروع می‌شود.
