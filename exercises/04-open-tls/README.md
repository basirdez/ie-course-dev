# تمرین ۴: TLS را با کلید خودتان باز کنید

> جلسهٔ ۴ · مهلت: شب پیش از جلسهٔ ۵

## هدف

برای سرور محلی خودتان گواهی بسازید، ببینید مرورگر و curl دقیقاً چه چیزهایی را می‌سنجند، و بعد خودتان جای ناظر شبکه بنشینید: یک بار بدون کلید و یک بار با کلید. در پایان باید بتوانید بگویید TLS چه چیزی را از چه کسی پنهان می‌کند و چه چیزی را نه.

## پیش‌بینی (سر کلاس نوشتید؛ همان را در README بیاورید)

در ضبط یک اتصال TLS 1.3، **بدون کلید**، کدام‌ها به‌صورت متن ساده دیده می‌شوند: نام سرور، گواهی سرور، مسیر URL، کوکی؟ چرا؟

## کار پایه

فایل‌های `starter/` را بردارید. به OpenSSL و Node 22 و curl نیاز دارید؛ روی Windows با نصب Git Bash، ابزار OpenSSL هم نصب می‌شود.

```sh
sh make-certs.sh          # یک CA آزمایشی، یک گواهی برای shop.test و یک گواهی منقضی‌شده
node server.mjs           # https://shop.test:8443
```

**بخش اول: یک اتصال درست را بخوانید.** خروجی این دستور را در `evidence/ok.txt` بگذارید و از روی آن بنویسید: نسخهٔ TLS، گروه تبادل کلید، پروتکلی که با ALPN انتخاب شد، نام‌های درون گواهی، و تاریخ انقضا.

```sh
curl -sv --cacert certs/ca.pem --resolve shop.test:8443:127.0.0.1 https://shop.test:8443/
```

**بخش دوم: اتصال را سه جور بشکنید.** برای هر حالت، خطای دقیق curl را در `evidence/broken.txt` بگذارید و در یک جمله بگویید کدام بررسیِ اسلاید «چه کسی می‌گوید این کلید مال این نام است؟» رد شده است.

| حالت | دستور |
| --- | --- |
| امضاکنندهٔ ناشناس | همان دستور، بدون `--cacert` |
| نام ناهمخوان | همان سرور با نام `bank.test`: مقدار `--resolve` و URL را عوض کنید |
| گواهی منقضی | سرور را با `CERT=old node server.mjs` اجرا کنید |

**بخش سوم: جای ناظر شبکه بنشینید.** برنامهٔ `tap.mjs` روی پورت 8444 گوش می‌دهد، همه‌چیز را دست‌نخورده به 8443 می‌فرستد و بایت‌های خام هر دو جهت را در فایل می‌نویسد؛ همان چیزی که هر دستگاه میان راه می‌بیند.

```sh
node tap.mjs
curl -s --cacert certs/ca.pem --resolve shop.test:8444:127.0.0.1 -H 'Cookie: sid=TOPSECRET' https://shop.test:8444/secret-path
node find.mjs conn1 shop.test TOPSECRET secret-path "IE Class Test CA" h2
```

همین را یک بار دیگر با `--tls-max 1.2` تکرار کنید (`conn2`) و جدول را پر کنید:

| رشته | در TLS 1.3 دیده شد؟ در کدام جهت؟ | در TLS 1.2 |
| --- | --- | --- |
| `shop.test` (نام سرور) | | |
| `IE Class Test CA` (از درون گواهی) | | |
| `secret-path` (مسیر) | | |
| `TOPSECRET` (کوکی) | | |
| `h2` (پروتکل ALPN) | | |

پیش‌بینی خودتان را با این جدول مقایسه کنید و هر اختلاف را توضیح دهید.

## چالش

- **با کلید خودتان باز کنید.** ترافیک پورت 8443 را با Wireshark ضبط کنید (روی رابط loopback) و curl را با `SSLKEYLOGFILE=keys.log` اجرا کنید. در Wireshark فایل `keys.log` را در تنظیمات TLS معرفی کنید و خط `cookie: sid=TOPSECRET` را در ترافیک بازشده پیدا کنید. اسکرین‌شات و سه خط اول `keys.log` (بدون مقدار رازها) را در `evidence/` بگذارید. نام هر برچسب در این فایل چه می‌گوید؟
- **ویژگی forward secrecy.** حالا `keys.log` را کنار بگذارید و فرض کنید فقط کلید خصوصی سرور (`certs/shop.key`) را دارید. با آن می‌شود همان ضبط را باز کرد؟ با استدلال از اسلاید «کلید مشترک چطور ساخته می‌شود» جواب دهید و در Wireshark امتحان کنید.

## امتیازی

اگر curl شما HTTP/3 دارد (`curl --version` را ببینید)، به یک سایت عمومی که HTTP/3 دارد یک بار با `--http2` و یک بار با `--http3` وصل شوید؛ هدر `alt-svc` را پیدا کنید و زمان `time_appconnect` را با `-w` مقایسه کنید. اگر ندارد، در مرورگر ستون Protocol را در زبانهٔ Network روشن کنید و نشان دهید بار اول و دوم بازدید چه فرقی دارند.

## تصمیم مهندسی

برای سامانهٔ نوبت‌دهی آزمایشگاه در یک پاراگراف تصمیم بگیرید: گواهی از کجا و با چه عمری، تمدید چطور، HTTP/3 روشن باشد یا نه، و درخواست‌های کدام مسیرها اجازهٔ `0-RTT` داشته باشند.

## پل به جلسهٔ ۵

در چالش، با داشتن کلید نشست همه‌چیز را خواندید: مسیر، header‌ها و کوکی. سرویسی که TLS را به‌جای شما تمام می‌کند هم همین کلید را دارد. جلسهٔ ۵ دربارهٔ همین واسطه‌هاست: cache و proxy و CDN.
