# تمرین ۳: ورود با کوکی، و شکستن آن

> جلسهٔ ۳ · مهلت: شب پیش از جلسهٔ ۴

## هدف

یک ورود ساده با کوکی نشست بسازید، خودتان با CSRF به آن حمله کنید، و بعد جلوی حمله را بگیرید. در پایان باید بتوانید بگویید مرورگر کوکی را همراه کدام درخواست می‌فرستد، `SameSite` دقیقاً کدام مرز را می‌کشد، و چرا CORS جای دفاع سرور را نمی‌گیرد.

## پیش‌بینی (سر کلاس نوشتید؛ همان را در README بیاورید)

کوکی نشست `SameSite=Strict` است و سرور شما روی `http://localhost:8000`. صفحهٔ مهاجم یک فرم پنهان دارد که خودکار به `/transfer` ارسال می‌شود. اگر صفحهٔ مهاجم روی `http://localhost:9000` باشد حمله موفق می‌شود؟ روی `http://127.0.0.1:9000` چطور؟ چرا؟

## کار پایه

از `starter/server.mjs` (Node 22) شروع کنید، یا همین را با `http.server` در Python 3.11 بنویسید. از این تمرین به بعد ماژول HTTP زبان مجاز است، ولی کتابخانهٔ آمادهٔ نشست و چارچوب وب نه. سرور پورت را از آرگومان اول می‌گیرد و مقدار `SameSite` را از متغیر محیطی `SAMESITE` (پیش‌فرض `Lax`؛ مقدار `off` یعنی بدون این attribute).

| درخواست | پاسخ |
| --- | --- |
| `POST /login` با بدنهٔ فرم `user=ali` | `200` یا `303`، با `Set-Cookie` نشست: شناسهٔ تصادفی دست‌کم ۱۶ بایتی، `Path=/` و `HttpOnly` و `SameSite` |
| `GET /me` بدون نشست معتبر | `401` |
| `GET /me` با نشست | `200` با متن `user=ali balance=1000` |
| `POST /transfer` با بدنهٔ فرم `to=sara&amount=100` | بدون نشست `401`؛ با نشست `200` و موجودی کم می‌شود |
| `POST /logout` | نشست **در سرور** پاک می‌شود؛ همان کوکی دیگر کار نمی‌کند |
| `GET /` | یک صفحهٔ HTML با فرم ورود و فرم انتقال |

شناسهٔ نشست نباید از نام کاربر ساخته شود و دو ورود پیاپی باید دو شناسهٔ متفاوت بگیرند. سرور برای هر درخواست یک خط لاگ بنویسد: متد، مسیر، کوکی نشست داشت یا نه، و مقدار `Origin` و `Sec-Fetch-Site`.

خودآزمایی:

```sh
node server.mjs 8000           # یا: python3 server.py 8000
node check/check.mjs 8000      # در پنجرهٔ دیگر
```

حالا حمله کنید. صفحهٔ `evil/index.html` را بنویسید: یک فرم پنهان به `http://localhost:8000/transfer` که با بار شدن صفحه ارسال می‌شود. آن را با `python3 -m http.server 9000` از پوشهٔ `evil` سرو کنید. در مرورگر خودتان (نام و نسخه‌اش را بنویسید) در `http://localhost:8000` وارد شوید، صفحهٔ مهاجم را باز کنید و این جدول را پر کنید:

| کوکی نشست | مهاجم روی `http://127.0.0.1:9000` | مهاجم روی `http://localhost:9000` |
| --- | --- | --- |
| `SAMESITE=off` | موجودی عوض شد؟ | موجودی عوض شد؟ |
| `SAMESITE=Lax` | | |
| `SAMESITE=Strict` | | |

برای هر خانه، خط لاگ سرور را در `evidence/csrf.txt` بگذارید. اگر نتیجهٔ `off` با `Lax` فرق داشت، دو دقیقه صبر کنید و دوباره امتحان کنید؛ فرق را توضیح دهید.

کد را در `ex03/` مخزن خودتان بگذارید و خروجی خودآزمایی را در `evidence/check.txt`.

## چالش

- **دفاع دوم.** سرور `POST /transfer` را فقط وقتی بپذیرد که `Sec-Fetch-Site` برابر `same-origin` یا `none` باشد، یا این فیلد اصلاً نیامده باشد (کلاینت غیرمرورگر). جدول بالا را دوباره پر کنید و نشان دهید حمله از `localhost:9000` هم دیگر موفق نمی‌شود. خودآزمایی: `node check/check.mjs 8000 --csrf`. اگر token ضد CSRF را ترجیح می‌دهید، آن را هم می‌توانید بسازید؛ توضیح دهید کدام را کجا به کار می‌برید.
- **اجازهٔ خواندن.** مسیر `GET /api/me` را اضافه کنید که JSON برگرداند و فقط `http://localhost:9000` بتواند با کوکی آن را بخواند (`Access-Control-Allow-Origin` دقیق، `Access-Control-Allow-Credentials: true` و `Vary: Origin`). در کنسول مرورگر از هر دو نشانی مهاجم با `fetch(…, { credentials: 'include' })` امتحان کنید. بعد عمداً سرور را طوری عوض کنید که مقدار `Origin` را بازتاب دهد؛ چه چیزی عوض شد و چرا خطرناک است؟

## امتیازی

ترافیک loopback را هنگام ورود ضبط کنید (`sudo tcpdump -i lo -A port 8000` در Linux، یا Wireshark) و خطی را که کوکی نشست در آن دیده می‌شود در `evidence/capture.txt` بگذارید. در یک شبکهٔ واقعی، چه کسانی می‌توانند همین خط را ببینند؟

## تصمیم مهندسی

سامانهٔ نوبت‌دهی آزمایشگاه (موضوع پیش‌فرض پروژه) هم رابط وب دارد و هم API برای agent. در یک پاراگراف بنویسید: نشست رابط وب با چه کوکی‌ای ساخته شود (نام، attributeها، عمر)، API با چه مدرکی کار کند، و چرا این دو را یکی نمی‌کنید.

## پل به جلسهٔ ۴

در بخش امتیازی، کوکی نشست را به‌صورت متن ساده در شبکه دیدید. جلسهٔ ۴ دربارهٔ همین است: زیر HTTP چه می‌گذرد، و TLS دقیقاً چه چیزی را از چه کسی پنهان می‌کند.
