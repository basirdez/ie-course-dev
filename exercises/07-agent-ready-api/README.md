# تمرین ۷: API خودتان را برای agent آماده کنید

> جلسهٔ ۷ · مهلت: شب پیش از جلسهٔ ۸

## هدف

یک API نوبت‌دهی به شما داده می‌شود که برای کاربر انسانی کافی بود: نه سقف نرخ دارد و نه در برابر تکرار امن است. آن را برای کلاینتی آماده می‌کنید که خسته نمی‌شود و بعد از هر خطا دوباره می‌فرستد. بعد طرف دیگر را هم می‌نویسید: کلاینتی که درست retry می‌کند.

## پیش‌بینی (سر کلاس نوشتید؛ همان را در README بیاورید)

یک agent درخواست `POST /bookings` را فرستاد و پیش از رسیدن پاسخ، اتصال قطع شد. دوباره بفرستد یا نه؟ برای هر دو حالت بنویسید چه چیزی ممکن است خراب شود. بعد با سرور starter بیازمایید: اگر دوباره بفرستد، چه پاسخی می‌گیرد و به کاربر چه می‌گوید؟

## کار پایه

فایل‌های `starter/` را بردارید (Node 22؛ هیچ بسته‌ای لازم نیست):

```sh
QUOTA=5 WINDOW=2 node server.mjs      # http://127.0.0.1:8831
curl -s -H 'Authorization: Bearer agent-a' http://127.0.0.1:8831/slots
curl -si -H 'Authorization: Bearer agent-a' -H 'Content-Type: application/json' \
  -d '{"slot":"sat-09","name":"Sara"}' http://127.0.0.1:8831/bookings
```

سه کار با شماست:

1. **سقف نرخ در `server.mjs`.** هر token در هر `WINDOW` ثانیه فقط `QUOTA` درخواست. بیشتر از آن `429` می‌گیرد، با `Retry-After`. سقف هر token جداست.
2. **کلید idempotency در `server.mjs`.** اگر `POST /bookings` فیلد `Idempotency-Key` داشت و همین token قبلاً با همین کلید و همین بدنه درخواست داده بود، همان پاسخ قبلی برگردد و نوبت تازه ساخته نشود. همان کلید با بدنهٔ دیگر `422` بگیرد. کلید هر token جداست.
3. **تابع `callWithRetry` در `client.mjs`.** نسخهٔ starter هر پاسخ ناموفق را بی‌درنگ دوباره می‌فرستد. قاعده‌های رفتار درست در توضیح بالای همان فایل آمده است.

خودآزمایی (سرور را پیش از آن تازه بالا بیاورید):

```sh
node check/check.mjs
```

بعد اثر کلاینت را بر سرور اندازه بگیرید. سرور را با `node server.mjs | tee server.log` بالا بیاورید و هر بار این را اجرا کنید:

```sh
node storm.mjs starter/client.mjs     # ده agent هم‌زمان، با کلاینت بد
node storm.mjs client.mjs             # همان، با کلاینت شما
```

| کلاینت | چند agent موفق شد | زمان | سرور چند درخواست دید |
| --- | --- | --- | --- |
| نسخهٔ starter | | | |
| نسخهٔ شما | | | |

کد را در `ex07/` مخزن خودتان بگذارید، و خروجی خودآزمایی و جدول را در `evidence/`.

## چالش

- **سقف را پیش از رسیدن بگویید.** به همهٔ پاسخ‌ها `RateLimit-Policy` و `RateLimit` بیفزایید (قالبش در اسلاید «سرور چطور می‌گوید الان نه؟»). بعد کلاینت را طوری عوض کنید که وقتی `r=0` دید، پیش از فرستادن درخواست بعدی صبر کند. با `storm.mjs` نشان دهید تعداد `429` چه تغییری کرد.
- **لایه‌های retry.** تابع `callWithRetry` را داخل یک حلقهٔ بیرونی بگذارید که خودش هم سه بار تلاش می‌کند، و به نشانی‌ای بفرستید که همیشه `503` می‌دهد. سرور چند درخواست دید؟ با عدد اسلاید «سه لایه، هر کدام سه تلاش» مقایسه کنید.

## امتیازی

سقف نرخ با پنجرهٔ ثابت یک ایراد دارد: کلاینت می‌تواند در مرز دو پنجره، در کمتر از یک ثانیه، دو برابر سقف بفرستد. با یک آزمایش نشانش دهید، و بعد سقف را با token bucket پیاده کنید. خودآزمایی باید هنوز سبز بماند.

## تصمیم مهندسی

یک agent سه ابزار دارد: `search_slots` (یک `GET`)، `book_slot` (یک `POST` به API شما)، و `send_sms` (یک `POST` به سرویس پیامک بیرونی که کلید idempotency نمی‌پذیرد). برای هر ابزار بنویسید: بعد از timeout دوباره فرستاده شود یا نه، چند بار، و اگر نمی‌دانیم اجرا شده یا نه، agent به کاربر چه بگوید.

## پل به فصل بعد

سرور شما شمارندهٔ سقف نرخ و پاسخ‌های ذخیره‌شدهٔ idempotency را در حافظهٔ یک پردازه نگه می‌دارد. اگر دو نسخه از این سرور پشت یک load balancer باشد، کدام آزمون‌های خودآزمایی ممکن است رد شوند و چرا؟ فقط یک بند بنویسید؛ پیاده‌سازی لازم نیست.
