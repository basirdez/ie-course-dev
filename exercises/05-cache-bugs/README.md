# تمرین ۵: باگ‌های cache را پیدا کنید

> جلسهٔ ۵ · مهلت: شب پیش از جلسهٔ ۶

## هدف

یک فروشگاه کوچک پشت یک cache مشترک به شما داده می‌شود. منطق برنامه درست است، ولی header‌های cache چهار باگ دارند. باید هر باگ را با آزمایش نشان دهید، فقط با header (و در یک مورد، با نشانی فایل) درستش کنید، و برای هر پاسخ به سه پرسش جلسه جواب بدهید: کلیدش چیست، تا کِی تازه است، و برای چه کسانی.

## پیش‌بینی (سر کلاس نوشتید؛ همان را در README بیاورید)

پاسخ `/search?q=book` برای کاربر فارسی‌زبان و انگلیسی‌زبان فرق دارد، ولی `Vary` ندارد. کاربر انگلیسی‌زبان، بعد از کاربر فارسی‌زبان، چه می‌بیند؟ کدام یک خط درستش می‌کند؟

## کار پایه

فایل‌های `starter/` را بردارید و در دو پنجره اجرا کنید (Node 22):

```sh
node origin.mjs      # فروشگاه:        http://127.0.0.1:8791
node proxy.mjs       # cache مشترک:   http://127.0.0.1:8790   (همان proxy دموی کلاس)
```

فایل `proxy.mjs` را عوض نکنید؛ همهٔ اصلاح‌ها در `origin.mjs` است. برای خالی کردن cache میان آزمایش‌ها: `curl -X POST http://127.0.0.1:8790/__purge`.

این چهار مسیر را از راه proxy با curl بیازمایید و برای هر کدام، باگ را با یک آزمایش دو یا سه درخواستی نشان دهید (خروجی curl با `-si` و خط‌های لاگ `origin` در `evidence/`):

| مسیر | رفتار درست |
| --- | --- |
| `/account` با کوکی `user=…` | هر کاربر صفحهٔ خودش را می‌بیند |
| `/search?q=book` با `Accept-Language: fa` یا `en` | هر زبان پاسخ خودش را می‌گیرد، و پاسخ هنوز در cache می‌ماند |
| `/` و `/assets/app.js` | بعد از انتشار نسخهٔ تازه (`curl -X POST http://127.0.0.1:8791/deploy`) کاربر بی‌درنگ اسکریپت تازه را می‌گیرد؛ ولی اسکریپتی که عوض نشده، یک سال در cache می‌ماند |
| `/price` | بعد از تغییر قیمت (`curl -X POST 'http://127.0.0.1:8791/price?value=135'`) قیمت تازه دیده می‌شود؛ و وقتی قیمت عوض نشده، سرور بدنه را دوباره نمی‌فرستد |

بعد `origin.mjs` را اصلاح کنید. خودآزمایی:

```sh
node check/check.mjs
```

برای هر چهار مسیر، جدول سه پرسش را پر کنید: کلید cache، عمر تازگی، و اینکه پاسخ در کدام cache (خصوصی، مشترک، هیچ) می‌ماند. کد را در `ex05/origin.mjs` مخزن خودتان بگذارید و خروجی خودآزمایی را در `evidence/check.txt`.

## چالش

- **راه‌حل تنبل.** اگر روی همهٔ پاسخ‌ها `Cache-Control: no-store` بگذارید، کدام آزمون‌های خودآزمایی رد می‌شوند؟ چرا این راه‌حل برای یک فروشگاه واقعی پشت CDN بد است؟ با شمردن خط‌های لاگ `origin` در ده بازدید از صفحهٔ اصلی نشان دهید.
- **نشانی فریبنده.** به مسیر `/account/x.css` درخواست بفرستید. سرور starter چه می‌دهد؟ حالا فرض کنید cache شما، مثل بعضی CDNها، هر نشانی‌ای را که به `.css` ختم شود بی‌توجه به header نگه دارد. سرور شما باید با چنین نشانی‌ای چه کند تا حملهٔ اسلاید «نشانی‌ای که CDN را گول زد» شدنی نباشد؟ پیاده کنید و نشان دهید.

## امتیازی

مسیر `/stream` پنج خط می‌فرستد، هر ثانیه یکی. آن را یک بار مستقیم (`curl -sN http://127.0.0.1:8791/stream`) و یک بار از راه proxy بگیرید و زمان رسیدن هر خط را ثبت کنید. چه فرقی دیدید؟ کدام خط از `proxy.mjs` مسئول آن است؟ proxy را طوری عوض کنید که این پاسخ را خط‌به‌خط رد کند (این تنها جایی است که اجازهٔ تغییر proxy دارید).

## تصمیم مهندسی

برای سامانهٔ نوبت‌دهی آزمایشگاه یک جدول بنویسید: پنج نوع پاسخ (صفحهٔ ورود، فهرست نوبت‌های خالی، صفحهٔ «نوبت‌های من»، فایل‌های ثابت، پاسخ API برای agent) و برای هر کدام `Cache-Control` و دلیلش. کدام یکی را به CDN می‌سپارید و کدام را هرگز؟

## پل به جلسهٔ ۶

در بخش امتیازی دیدید واسطه‌ای که منتظر «پاسخ کامل» می‌ماند، با پاسخی که ذره‌ذره می‌رسد چه می‌کند. جلسهٔ ۶ دربارهٔ همین است: وقتی سرور باید اول حرف بزند یا پاسخ را کم‌کم بفرستد.
